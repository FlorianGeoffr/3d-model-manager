# Findings: Prior Art & Frontend 3D Viewing (researched 2026-07-04)

## 1. Prior art

### Manyfold (the main comparable)
The dominant self-hosted 3D-print DAM. Ruby on Rails + Sidekiq + PostgreSQL, Bootstrap 5 frontend, THREE.js client viewer, Mittsu (Ruby THREE.js port) + assimp for server-side analysis; AGPL-3.0, ~2.1k stars, very active (v0.146.0 released 2026-07-02, 234 releases) ([GitHub](https://github.com/manyfold3d/manyfold)). Data model: a **Library** (a storage root — local disk or S3) contains **Models**; a *model is defined as a folder containing indexable files* — files at the library root are ignored, and nested folders create spurious models that must be manually merged ([discussion #5020](https://github.com/manyfold3d/manyfold/discussions/5020)). Models have files, tags, creators, collections, lists, likes, remix links, "duplicate file / nested model / inefficient format" problem-detection, and per-model version history; it can physically **reorganize files on disk from metadata** with templated renaming ([features](https://manyfold.app/features.html), [manyfold.app](https://manyfold.app/)). Imports metadata/files from Thingiverse, MyMiniFactory, Cults3D; sends pre-sliced GCODE to OctoPrint/Moonraker/PrusaLink; ActivityPub federation; OIDC multiuser; REST API. Notably, in Feb 2026 (v0.133.0) they **gave up on browser-side rendering for previews and integrated F3D to render static thumbnails server-side** because loading whole models in the browser was too heavy ([release notes](https://manyfold.app/news/2026/02/25/release-v0-133-0.html)). Known pain points: Bambu/production-extension 3MFs unsupported for years ([issue #2438](https://github.com/manyfold3d/manyfold/issues/2438), [issue #3202](https://github.com/manyfold3d/manyfold/issues/3202)), hangs on bulk uploads, folder-=-model heuristic confusion, and users wanting finer control over merge/split of models ([issue #4277](https://github.com/manyfold3d/manyfold/issues/4277)). **Lessons for us:** (a) don't make "folder = model" a rescan-time guess — our content-hash + explicit revision-folder design avoids Manyfold's merge/split mess; (b) generate thumbnails server-side, don't rely on the browser viewer for gallery images; (c) handle Bambu production-extension 3MFs from day one — it's their #1 format complaint.

### VanDAM
Not a separate product: VanDAM was Manyfold's original name (repo `Floppy/van_dam` now redirects to `manyfold3d/manyfold`; the renaming is visible in forks) ([GitHub redirect](https://github.com/Floppy/van_dam), [fork](https://github.com/DanozWorld/manyfold_3d_printed_asset_management)). Its founding heuristic — "any folder containing STL/OBJ files is a model" — is the ancestor of Manyfold's scan behavior. **Lesson:** the scan-a-messy-existing-tree use case was the original demand; our rescan-by-hash reconciliation serves the same need more robustly.

### printarr
`Schamper/printarr` — "prowlarr but for plastic". Python FastAPI + Vue/Vite + SQLite, Docker. Meta-searches Thingiverse, Printables, MakerWorld, Cults3D simultaneously with live streaming results; bookmark/tag library; print queue; and **slicer deep-link protocol handlers** (`prusaslicer://`, `orcaslicer://`, `bambustudio://`) to open a model directly in a desktop slicer. Effectively dead: 6 commits, 3 stars, no releases, last touched Mar 2024 ([GitHub](https://github.com/Schamper/printarr)). **Lessons:** the *arr-style search-then-import UX validates our import-by-URL feature, and "Open in Bambu Studio" via `bambustudio://open?file=...` URL handler is a cheap, high-value addition to our upload-sliced-file workflow.

### Bambuddy (the relevant "Polar Cloud alternative")
Polar Cloud itself is a cloud fleet-management service ([polar3d.com](https://polar3d.com/)); its self-hosted alternatives are printer-ops tools (OctoPrint, SimplyPrint (cloud), 3DPrinterOS) rather than libraries ([AlternativeTo](https://alternativeto.net/software/polar-cloud/)). The one that matters for us is **Bambuddy**: AGPL, Python FastAPI + SQLAlchemy + React/TypeScript/Tailwind, SQLite or Postgres, Three.js previews — almost exactly our stack. 2.4k stars, v0.2.4.8 (2026-06-28), very active. It talks to Bambu printers (incl. **A1 mini**) over LAN via **FTPS for file upload + TLS MQTT for control/status**, requiring the printer's Developer/LAN mode; also does MakerWorld URL import, STL thumbnail auto-generation, print archive, queue/scheduling, AMS mapping ([GitHub](https://github.com/maziggy/bambuddy), [Tailscale writeup](https://tailscale.com/blog/bambuddy-bambu-lab-3d-printer-access)). **Lessons:** proven reference implementation for our "send .gcode.3mf to A1 mini over LAN" feature (FTPS upload + MQTT `project_file` print command), and evidence the FastAPI+React+Tailwind stack scales to this exact domain. Note its issue tracker shows firmware FTPS quirks (550 errors on some models) — treat printer I/O defensively.

### Obico
Community-built open-source smart-printing platform (ex-Spaghetti Detective): webcam-based **AI print-failure detection**, remote access, notifications; self-hostable with the ML model running locally; OctoPrint/Klipper-focused, next-gen detection model GA May 2026 ([obico-server](https://github.com/TheSpaghettiDetective/obico-server), [blog](https://www.obico.io/blog/next-gen-ai-failure-detection-general-release/)). It is *not* a model manager. **Lesson:** monitoring/failure-detection is a separate, well-served product category — keep it out of scope; if the user ever wants it, it coexists with our app rather than competing.

## 2. Browser 3D viewing

### three.js loaders (three r185 current)
- **STLLoader** (addon): reliable for binary STL, the common case. Known issues: ASCII STL parsing historically memory-hungry ([issue #13540](https://github.com/mrdoob/three.js/issues/13540)); parsing happens on the main thread (multi-second freeze for million-triangle files); output is unindexed triangle soup (no vertex sharing, no smooth normals until you `mergeVertices`). A 100MB binary STL ≈ 2.1M triangles ≈ ~150MB of Float32 position+normal attributes in RAM/VRAM.
- **OBJLoader**: fine for geometry; MTL/texture handling is fiddly but irrelevant for print models.
- **ThreeMFLoader**: supports the 3MF **core spec** plus *partial* Materials & Properties extension (vertex colors, textures, PBR) — and **no Production Extension** ([three.js docs](https://threejs.org/docs/pages/ThreeMFLoader.html)). This matters a lot: **Bambu Studio saves project 3MFs (and .gcode.3mf) with the Production Extension by default**, which is exactly why other tools fail to open them ([Bambu wiki](https://wiki.bambulab.com/en/software/bambu-studio/3mf-compatibility)); Manyfold hit the same wall ([#2438](https://github.com/manyfold3d/manyfold/issues/2438)). The loader is also brittle on edge-case files generally (e.g. [#27947](https://github.com/mrdoob/three.js/issues/27947), [large-3MF forum thread](https://discourse.threejs.org/t/problem-loading-large-3mf-files-in-three-js/38463)). Verdict: OK for "generic/export 3MF" (e.g. MakerWorld downloads that use core spec), **not trustworthy for Bambu project/sliced 3MFs**.
- Special case — **sliced `.gcode.3mf`**: don't try to mesh-render it at all. It's a ZIP whose payload is `Metadata/plate_N.gcode` plus **four ready-made PNGs per plate** (`plate_N.png`, `plate_N_no_light.png`, `top_plate_N.png`, `pick_plate_N.png`) and `slice_info.config` (filament, time estimates) ([Printago format writeup](https://printago.io/blog/3mf-file-format)). Extract the PNGs as the thumbnail and show slice metadata — that's what the printer itself does.
- **GLTFLoader**: the flagship, best-maintained loader; the only one with a compression story (Draco, `EXT_meshopt_compression`, KTX2) ([docs](https://threejs.org/docs/pages/GLTFLoader.html)).

### react-three-fiber + drei — version/compat status (verified against npm registry, July 2026)
- `@react-three/fiber` latest is **9.6.1** (2026-04-28); peer deps `react >=19 <19.3`, `three >=0.156`. **R3F v9 requires React 19.** R3F is explicitly compatible with React 19.0–19.2 (the 19.2 reconciler bump was absorbed) ([releases](https://github.com/pmndrs/react-three-fiber/releases), [v9 migration guide](https://r3f.docs.pmnd.rs/tutorials/v9-migration-guide)).
- `@react-three/drei` latest is **10.7.7**; peers `react ^19`, `@react-three/fiber ^9`. **Stage, Bounds, OrbitControls all present and current** in drei v10 ([Stage docs](https://drei.docs.pmnd.rs/staging/stage), [drei React-19 compat discussion](https://github.com/pmndrs/drei/discussions/2213)).
- The **React 18 line is frozen**: last releases were fiber **8.18.0** and drei **9.122.0**, both 2025-02-19, no updates since. ⚠️ **This conflicts with the confirmed "React 18" stack decision.** Building new in mid-2026 on React 18 means a dead R3F/drei branch. Recommend **React 19** (latest 19.2.7; TanStack Query, shadcn, Tailwind v4 all support it). If React 18 is truly fixed, pin `fiber@8.18.0` + `drei@9.122.0` and accept no upstream fixes.

### model-viewer alternative
`@google/model-viewer` **4.3.1**, still actively maintained (releases through mid-2026, internally on three r174) ([GitHub](https://github.com/google/model-viewer), [releases](https://github.com/google/model-viewer/releases)). One `<model-viewer src=... camera-controls>` tag gives orbit/zoom, auto-framing, poster images. But it renders **glTF/GLB only** — every format would need server conversion first, and per-format fallback rendering (fresh uploads before the worker converts) becomes impossible. Fine as a plan-B if we want zero three.js code; R3F gives more control for the same GLB input.

### 100MB+ STL performance guidance
Consensus: don't ship raw 100MB STLs to the browser — parse freeze, ~2× memory during load, no compression ([forum](https://discourse.threejs.org/t/problem-loading-large-3mf-files-in-three-js/38463), [CAD optimization writeup](https://rapidmade.com/webgl-three-js-cad-rendering-optimization/)). Server-side pipeline (all verified current on npm):
- **gltfpack / meshoptimizer 1.2.0**: `gltfpack -i in.glb -o out.glb -cc` → quantization + `EXT_meshopt_compression`; typically 10–20× smaller than STL; optional `-si 0.5` mesh simplification for a lightweight preview LOD. Meshopt decode is very fast with a tiny (~tens of KB) WASM decoder.
- **gltf-transform 4.4.1** (`@gltf-transform/cli`): scriptable alternative — `gltf-transform optimize` bundles weld/quantize/meshopt or Draco. Draco compresses pure geometry slightly better but decodes slower with a ~300KB decoder; for print-model meshes **meshopt is the better default** ([three.js GLTFLoader docs on both extensions](https://threejs.org/docs/pages/GLTFLoader.html), [compression discussion](https://discourse.threejs.org/t/compression-draco-ktx2-example/31382)).
- If native STL parsing in-browser is kept for small files, do it in a Web Worker to avoid main-thread freezes; only bother with SharedArrayBuffer zero-copy if profiling demands it (requires COOP/COEP headers).

## 3. Recommendation

**Normalize to GLB server-side; render one format in the viewer.** The Celery worker already converts STEP/IGES — extend that into a universal rule: for every uploaded/scanned mesh file, generate (a) a GLB derivative via meshopt (`trimesh`/`lib3mf` load → export glTF → `gltfpack -cc`, plus a `-si` decimated preview LOD above ~1–2M triangles), and (b) a static PNG thumbnail from the same asset (Manyfold's F3D move validates this). Per-format handling:

| Source | Viewer path |
|---|---|
| STL, OBJ, generic/core-spec 3MF | GLB derivative (native STLLoader/OBJLoader fallback only for "just uploaded, conversion pending", small files) |
| Bambu project 3MF (production ext.) | **server-side only** — lib3mf (supports Production Extension) → GLB; never ThreeMFLoader |
| Sliced `.gcode.3mf` | no mesh render; extract `Metadata/plate_N.png` thumbnails + `slice_info.config` metadata |
| STEP/IGES | already converted server-side → GLB |

**Viewer component:** one `<ModelViewer3D url=... />` built on **@react-three/fiber 9 + drei 10** (requires React 19 — flag the stack change): `<Canvas frameloop="demand">` (battery-friendly for a view-only viewer) + drei `<Stage>` (studio lighting, centering, shadows) + `<OrbitControls makeDefault>` + `useGLTF` with `MeshoptDecoder` registered; `<Bounds fit clip>` for zoom-to-fit on model switch. This is ~50 lines and covers everything once GLB is the lingua franca.

## 4. shadcn/ui + Tailwind v4 + Vite + React — mid-2026 scaffolding norms

Breaking changes vs 2024 that affect scaffolding (all from shadcn's own docs):
- **Tailwind v4** (latest 4.3.2): CSS-first config — no `tailwind.config.js`; `@import "tailwindcss";` in CSS, theme via `@theme` / `@theme inline` CSS variables (OKLCH colors), and the **`@tailwindcss/vite` plugin** instead of PostCSS ([shadcn Tailwind v4 docs](https://ui.shadcn.com/docs/tailwind-v4), [Feb 2025 changelog](https://ui.shadcn.com/docs/changelog/2025-02-tailwind-v4)).
- **shadcn components**: `forwardRef` removed (React 19 style, `React.ComponentProps` types), every primitive has a `data-slot` attribute, `tailwindcss-animate` deprecated in favor of `tw-animate-css`, toast deprecated in favor of sonner.
- **CLI**: package is `shadcn` (not `shadcn-ui`), now at **4.x** (CLI 3.0 Aug 2025 added namespaced registries + MCP server; CLI 4 Mar 2026). Init: `npx shadcn@latest init -t vite`, or the `shadcn/create` preset builder ([Vite install docs](https://ui.shadcn.com/docs/installation/vite), [changelog](https://ui.shadcn.com/docs/changelog)).
- ⚠️ **As of July 2026, `shadcn init` defaults to Base UI primitives, not Radix.** Radix remains fully supported — pass **`-b radix`** for the Radix flavor (relevant since our spec says "shadcn/Radix"; either pick Base UI or pin the flag in scaffolding scripts) ([July 2026 changelog](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)).
- **Vite 8** (latest 8.1.3, released Mar 2026): Rolldown (Rust) replaces Rollup/esbuild for everyone — 10–30× faster builds, `build.rollupOptions` → `build.rolldownOptions`, oxc replaces esbuild transforms, Lightning CSS minification, stricter circular-import warnings ([Vite 8 announcement](https://vite.dev/blog/announcing-vite8), [migration guide](https://vite.dev/guide/migration)). New projects should start on Vite 8 directly.
- **TanStack Query v5 is the current stable line** — no v6 exists or is tagged; latest `@tanstack/react-query` **5.101.2** (2026-06-27), peer `react ^18 || ^19` (verified on npm registry). Safe to build on; works with either React major.

**Net stack adjustment to propose:** React **19.2** + Vite 8 + Tailwind 4 + shadcn CLI 4 (`-b radix` if Radix is a hard requirement) + TanStack Query 5 + R3F 9 / drei 10 / three r185.
