# Findings: Pluggable storage abstraction (local / SMB / S3) for streaming 1–500 MB model files — as of mid-2026

## 1. fsspec vs. wrapping smbclient + boto3 yourself

### fsspec SMBFileSystem (smbprotocol-based)
- It is a thin, **sync-only** wrapper over `smbprotocol`'s high-level `smbclient` API. Verified from current source ([fsspec smb.py](https://github.com/fsspec/filesystem_spec/blob/master/fsspec/implementations/smb.py), [rendered docs](https://filesystem-spec.readthedocs.io/en/latest/_modules/fsspec/implementations/smb.html)):
  - `__init__(host, port=None, username=None, password=None, timeout=60, encrypt=None, share_access=None, register_session_retries=4, register_session_retry_wait=1, register_session_retry_factor=10, auto_mkdir=False, **kwargs)` — **no `auth_protocol` parameter**. Auth is username/password (NTLM/negotiate) or "anonymous or integrated"; Kerberos is only reachable implicitly via `smbprotocol[kerberos]` ambient config (`ClientConfig`), not through the fsspec constructor.
  - Session registration has exponential-backoff retry; auth errors are not retried, only network errors.
  - `copy()` calls `smbclient.copyfile()` → **server-side copy** (see §3).
  - `ls(detail=True)` calls `smbclient.listdir()` then `smbclient.stat()` **per entry** — an N+1 round-trip pattern that is slow on large trees. `smbprotocol` 1.16.0 added `SMBDirEntry.smb_info` specifically to avoid extra stat calls in `scandir` ([changelog](https://github.com/jborean93/smbprotocol/blob/master/CHANGELOG.md)), but fsspec's `ls` does not use it. For your rescan/reconcile feature, direct `smbclient.scandir()` is markedly faster.
- Real-world reliability: usable but the least-polished fsspec backend. Documented bugs like the `_as_unc_path` URL-mangling issue that broke Prefect's SMB support ([PrefectHQ/prefect #10694](https://github.com/PrefectHQ/prefect/issues/10694)); the code itself carries comments that the retryable-exception set is still being discovered. It is maintained (retry logic reworked in 2025 releases) but has far fewer users than s3fs.
- Performance: pure-Python protocol stack; reads via `smbclient` measured at roughly **half the speed of kernel cifs mounts**, with the author noting Python will never match C implementations ([smbprotocol #91](https://github.com/jborean93/smbprotocol/issues/91)). For a single home user streaming 1–500 MB files on a LAN this is fine (typically saturates or near-saturates 1 GbE for large sequential reads with big buffer sizes; small-file metadata ops are the slow part).
- `smbprotocol` itself is healthy: **v1.16.1, 2026-04-02**; SMB 2.0.2–3.1.1 dialects, signing, SMB3 encryption (default on), DFS, NTLM everywhere + Kerberos via pyspnego/gssapi/pykrb5 with `auth_protocol` = negotiate/kerberos/ntlm on `ClientConfig` ([PyPI](https://pypi.org/project/smbprotocol/), [releases](https://github.com/jborean93/smbprotocol/releases)).

### s3fs
- Mature, actively maintained (2025.12.x line), the reference `AsyncFileSystem` implementation alongside HTTP ([docs](https://s3fs.readthedocs.io/), [source](https://github.com/fsspec/s3fs/blob/main/s3fs/core.py)).
- Big operational caveat: it depends on **aiobotocore, which hard-pins botocore**, causing chronic resolver conflicts with independently-pinned boto3 in the same venv ([aiobotocore #840](https://github.com/aio-libs/aiobotocore/issues/840), [s3fs #357](https://github.com/fsspec/s3fs/issues/357)). If any other part of your app uses boto3, expect friction.
- Write path buffers parts in memory: `default_block_size = 50 * 2**20` (50 MB) per open write stream (verified in [core.py](https://github.com/fsspec/s3fs/blob/main/s3fs/core.py)); tune down (S3 minimum part size is 5 MB) or you pay ~50 MB RAM per concurrent upload.

### LocalFileSystem
- Trivial and solid; nothing to flag except that its `cp_file` is `shutil`-based full data copy (no reflink — see §3).

### Verdict
For **three fixed backends and a narrow operation set** (open-read-stream, write-stream, list, stat, delete, copy, move, exists), **wrap the native clients behind your own ~8-method `StorageBackend` Protocol**: `pathlib`/`os` for local, `smbclient` high-level API directly for SMB, and boto3 (or obstore, below) for S3. Reasons:
- You will need backend-specific escapes anyway: local reflink cloning (§3), `smbclient.scandir` for fast rescans, S3 presigned URLs or ranged GETs for the 3D viewer, per-backend atomic-write semantics (§5).
- fsspec's main value (dozens of backends, glob, uniform URLs) is not needed here; its costs (sync SMB, aiobotocore pinning, caching foot-guns in §5, lowest-common-denominator semantics) are real.
- A serious 2025+ alternative for the S3 leg: **obstore** (developmentseed, Rust `object_store` bindings) — zero Python dependencies, sync + async APIs, file-like streaming, benchmarked ~9x fsspec throughput on many concurrent small requests; explicitly positions itself against fsspec's "object storage is not a filesystem" impedance mismatch ([GitHub](https://github.com/developmentseed/obstore), [alternatives page](https://developmentseed.org/obstore/latest/alternatives/), [launch post](https://developmentseed.org/blog/2025-08-01-obstore/)).
- fsspec is still a *sane* fallback if you accept sync-in-threadpool everywhere and pin s3fs+aiobotocore carefully; it notably gives you SMB server-side copy and SMB atomic-rename writes for free (its `SMBFileOpener` and `copy()` are correctly implemented). But you'd be wrapping fsspec in your own interface regardless — so wrap the natives.

## 2. Streaming through FastAPI without whole-file buffering

- **Uploads.** FastAPI/Starlette `UploadFile` is a `SpooledTemporaryFile`: RAM-bounded (spools to disk beyond a small threshold) but it double-writes via server temp disk. Two better options:
  - Raw-body endpoint (`PUT`) consuming `async for chunk in request.stream()` — true zero-copy streaming, no multipart parsing ([FastAPI #2578 discussion](https://github.com/fastapi/fastapi/issues/2578), [python.org discussion of FastAPI→S3 without intermediate file](https://discuss.python.org/t/file-upload-in-fastapi-and-from-there-to-s3-without-intermediate-file/51259)).
  - If you must keep multipart forms, `streaming-form-data` parses multipart incrementally as bytes arrive ([practical guide](https://python.plainenglish.io/streaming-file-uploads-and-downloads-with-fastapi-a-practical-guide-ee5be38fdd66)).
  - ~1 MB chunks are the sweet spot ([oneuptime guide, 2026](https://oneuptime.com/blog/post/2026-01-26-fastapi-file-uploads/view)).
  - Backend writes are sync (smbclient/boto3/local) — push chunks to the writer via `anyio.to_thread.run_sync` (or an async-generator→thread bridge). boto3's `upload_fileobj` accepts a file-like and does concurrent multipart internally; feed it a pipe/wrapper around the request stream.
  - **Pragmatic homelab pattern worth adopting:** spool the upload to a local temp file first anyway — you need local bytes for hashing (§4), thumbnail generation, and 3MF/G-code metadata extraction — then let the Celery worker stream it to the destination backend. This sidesteps most async plumbing at the cost of temp disk.
- **Downloads.** `StreamingResponse` with a chunk generator; Starlette iterates *sync* iterators in a threadpool automatically, so wrapping `smbclient.open_file(...)` / boto3 `Body.iter_chunks()` in a plain generator is safe and non-blocking.
- **fsspec async status:** only `HTTPFileSystem` is async among built-ins; s3fs is a true `AsyncFileSystem` (with experimental `AbstractAsyncStreamedFile` / `open_async`); **SMB and Local are sync-only**, with an *experimental* `AsyncFileSystemWrapper` (threadpool shim) ([fsspec async docs](https://filesystem-spec.readthedocs.io/en/latest/async.html)). So "one async fsspec interface over all three" does not really exist — you'd be threadpooling SMB/local regardless, which is another argument for your own interface with an explicit `run_sync` boundary.

## 3. Fast full-snapshot copy per revision

- **SMB — yes, server-side copy works.** `smbclient.copyfile()` issues SMB2 `FSCTL_SRV_COPYCHUNK` (constants and IOCTL implemented in [smbprotocol/ioctl.py](https://github.com/jborean93/smbprotocol/blob/4f7b81bebfa2f681d3ea645d4728c32b35bf5a2c/smbprotocol/ioctl.py/)); since **v1.16.1 it falls back to client-side copy on `STATUS_NOT_SUPPORTED`** (previously crashed against NetApp ONTAP — [issue #178](https://github.com/jborean93/smbprotocol/issues/178), [changelog](https://github.com/jborean93/smbprotocol/blob/master/CHANGELOG.md)). Server support: Samba ≥ 4.1, **enabled by default**; Windows Server 2012+; and on Samba+btrfs the `vfs_btrfs` module turns COPYCHUNK into a **clone-range reflink — no data traverses network *or* disk**, source and destination share extents ([Samba wiki: Server-Side Copy](https://wiki.samba.org/index.php/Server-Side_Copy)). For a homelab NAS this makes revision snapshots near-instant. fsspec's `SMBFileSystem.copy()` inherits this since it calls `smbclient.copyfile`.
- **S3 — yes.** `CopyObject` is a single atomic server-side copy up to 5 GB (all your files, at ≤500 MB, qualify); above that it's multipart `UploadPartCopy` ([AWS CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html), [UploadPartCopy](https://docs.aws.amazon.com/AmazonS3/latest/API/API_UploadPartCopy.html)). s3fs also does this correctly through fsspec: `_cp_file` switches to managed multipart copy above `MANAGED_COPY_THRESHOLD = 150 MiB` (verified in [s3fs core.py](https://github.com/fsspec/s3fs/blob/main/s3fs/core.py)). Works on MinIO too.
- **Local — reflinks need your own code.** Python stdlib `shutil` still does **not** reflink (long-open [bpo-37157 / gh-81338](https://bugs.python.org/issue37157), still under discussion in 2025 [on discuss.python.org](https://discuss.python.org/t/shutil-copy2-reflink/92077)); fsspec LocalFileSystem therefore does full data copies. But Python ≥ 3.12 exposes `fcntl.FICLONE`, so a reflink clone is ~3 lines: open src+dst, `fcntl.ioctl(dst.fileno(), fcntl.FICLONE, src.fileno())`, fall back to `shutil.copyfile` on `OSError` (EXDEV/EOPNOTSUPP on non-btrfs/XFS) ([fcntl docs](https://docs.python.org/3/library/fcntl.html), [ioctl_ficlone(2)](https://manpages.debian.org/testing/manpages-dev/ioctl_ficlone.2.en.html)). The [`reflink` PyPI package](https://pypi.org/project/reflink/) wraps the same (plus APFS clonefile) if you prefer a dependency.
- **Conclusion:** a `copy_file(src, dst)` method on your own interface routes to three genuinely fast paths (COPYCHUNK / CopyObject / FICLONE-with-fallback). Through fsspec you get 2 of 3; the local reflink path always needs custom code.

## 4. Content hashing

- **blake3 is production-ready:** [PyPI `blake3`](https://pypi.org/project/blake3/) **v1.0.9 (2026-06-22)**, actively maintained Rust/PyO3 bindings, prebuilt wheels for most platforms (no Rust toolchain needed), hashlib-compatible API, `max_threads=blake3.AUTO` multithreading (worth it above ~1 MB inputs — i.e., all your files), and `update_mmap(path)` for fast whole-file hashing of local files ([GitHub](https://github.com/oconnor663/blake3-py), [releases](https://github.com/oconnor663/blake3-py/releases)).
- **Tee-while-streaming pattern:** in the upload chunk loop, `hasher.update(chunk)` before writing the chunk to the backend — the hash is free (BLAKE3 runs multi-GB/s, far faster than any LAN link), and you know the content hash the moment the write finishes, before committing the DB row. Same pattern in reverse for verify-on-download.
- **Rescan economics:** reconciling relocations on SMB/S3 means re-reading bytes over the network to hash. Store `(size, mtime/ETag) → hash` in Postgres and only re-hash entries whose size/mtime changed or that appear at unknown paths; treat equal-size+mtime as "probably same, verify lazily". Note S3 ETags are not content hashes for multipart uploads, so don't rely on them as identity.

## 5. Gotchas

- **SMB from Docker:** a userspace client (smbprotocol) is a major win over kernel CIFS mounts — it needs only an **outbound TCP 445** connection, no `--cap-add SYS_ADMIN`/privileged container, no volume plugins ([CIFS-in-container setup pain for comparison](https://linuxvox.com/blog/mount-smb-cifs-share-within-a-docker-container/)). Remaining traps: (a) **name resolution** — NetBIOS/WS-Discovery/mDNS don't work from the container's network; use the NAS IP or a real DNS name, or `extra_hosts:` in compose; (b) credentials via env/secrets, passed to `smbclient.register_session()` or per-call kwargs; (c) if you ever enable Kerberos, you need correct DNS + NTP sync — for a homelab NAS just use NTLM over SMB3 with encryption (smbprotocol default) ([smbprotocol README](https://github.com/jborean93/smbprotocol)); (d) **Celery prefork fork-safety**: `smbclient` keeps a global connection/session pool keyed by server — never establish sessions at import time in the parent; connect lazily per worker process, and call `reset_connection_cache()`/`delete_session` on worker shutdown.
- **fsspec caching pitfalls** (if you do use fsspec): (a) **instance caching** — filesystems with identical constructor args return the same cached instance (`skip_instance_cache=True` to opt out), which can silently share connections across your app; (b) **listings cache staleness** — directory listings are cached and only invalidated by writes *through the same instance*; external writes (your user rearranging the NAS share by hand — exactly your rescan use case) are invisible until `invalidate_cache()`/`ls(refresh=True)`/`use_listings_cache=False` ([fsspec features docs](https://filesystem-spec.readthedocs.io/en/latest/features.html), [dircache](https://filesystem-spec.readthedocs.io/en/latest/_modules/fsspec/dircache.html)). Any rescan job must start by invalidating caches or it will reconcile against stale trees.
- **Atomic write patterns per backend:**
  - **Local:** classic write-temp-then-`os.replace()` in the same directory — fully atomic on POSIX.
  - **SMB:** `smbclient.replace()` (SetInfo rename with replace-if-exists) gives you the same pattern; fsspec's `SMBFileOpener` already does exactly this (UUID temp file, `smbclient.replace` on commit) — copy that design ([fsspec smb.py](https://github.com/fsspec/filesystem_spec/blob/master/fsspec/implementations/smb.py)).
  - **S3:** there is no rename ("rename" = copy+delete, non-atomic and double-cost — avoid). Instead rely on S3's own guarantee: an object is **never visible partially** — a PUT or CompleteMultipartUpload either fully materializes the key or nothing does. So on S3, write directly to the final key and treat the DB commit as your transaction boundary; an aborted multipart upload leaves invisible garbage parts (set a bucket lifecycle rule to expire incomplete MPUs).
  - fsspec's cross-backend "transactions" are explicitly documented as "semi-atomic" and partially implemented — don't build correctness on them ([features docs](https://filesystem-spec.readthedocs.io/en/latest/features.html)).
- **Version pinning:** if you take s3fs, pin `s3fs`+`aiobotocore` as a matched pair and keep boto3 out of the same env (or use the `aiobotocore[boto3]` extra); mixing free-floating boto3 with s3fs is the #1 reported packaging failure ([aiobotocore #840](https://github.com/aio-libs/aiobotocore/issues/840)).

## Bottom-line recommendation

Define your own small `StorageBackend` Protocol (open_read_stream, write_stream(chunks)→hash, list_tree, stat, delete, copy_file, move_file, exists). Implement it three times: **local** = pathlib + FICLONE-then-fallback copy; **SMB** = `smbclient` high-level API directly (scandir with `smb_info` for rescans, `copyfile` for COPYCHUNK snapshots, `replace()` for atomic writes, lazy per-process sessions); **S3** = boto3 `upload_fileobj`/`get_object`/`copy` (or obstore for a cleaner async story). Run all backend I/O behind an explicit threadpool boundary from FastAPI, hash with blake3 in the streaming loop, and spool uploads to local temp since thumbnails/metadata extraction need local bytes anyway. fsspec is workable but you would out-grow it in exactly the places that matter here (local reflinks, SMB scan performance, async, atomicity semantics), while its SMB layer is the least battle-tested part of the stack.
