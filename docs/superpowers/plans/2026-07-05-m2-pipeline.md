# M2 Implementation Plan — Processing Pipeline: Metadata, Thumbnails, GLB, Viewer

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Every uploaded file gets extracted metadata, thumbnails, and a browser-viewable GLB; the gallery shows real thumbs + badges; the model page gets a rotate/zoom/pan 3D viewer and a sliced-file plate panel.

**Architecture:** A per-blob Celery step pipeline (`extract_metadata → extract_embedded_thumbs → convert_to_glb → optimize_glb → render_thumb`, format-dependent) kicked off by the existing `store_to_backend` task, writing to the existing `blob_meta` / `derivatives` / `assembly_thumbs` tables (no schema change). Derivatives are local files under `{data_dir}/derivatives/`, served by new immutable-cached `/api/blobs/...` endpoints. Frontend: R3F viewer (GLB-only, code-split), gallery thumbs/badges, plate panel.

**Tech stack:** trimesh(+lxml) · lib3mf 2.5 · cascadio (STEP) · cadquery-ocp 7.9 (IGES) · f3d 3.5 + OSMesa · gltfpack 1.2 (meshopt `-cc`) · Pillow · three r185 + @react-three/fiber 9.6 + @react-three/drei 10.7.

Read the SPEC sections "Processing pipeline", "API surface", "Frontend", and the research doc `docs/research/research-tooling.md` (RESEARCH) before implementing — RESEARCH has the exact f3d snippet, Bambu 3MF zip layout, and slice_info key names.

- **Originals are immutable:** pipeline reads library bytes via `StorageBackend.read`, never writes to the backend. GLB conversion NEVER rescales or reorients — true dimensions live in `blob_meta` (mm); the viewer normalizes framing client-side.
- **Pipeline shape (single source of truth):** per-BLOB steps, format-keyed map `PIPELINE_STEPS` (final state; Tasks 3–6 fill in the step implementations):

  | BlobFormat | Steps in order |
  |---|---|
  | `stl`, `obj` | extract_metadata → convert_to_glb → optimize_glb → render_thumb |
  | `3mf` | extract_metadata → extract_embedded_thumbs → convert_to_glb → optimize_glb → render_thumb |
  | `gcode_3mf` | extract_metadata → extract_embedded_thumbs |
  | `gcode` | extract_metadata |
  | `step`, `iges` | convert_to_glb → extract_metadata → optimize_glb → render_thumb |
  | `png`, `jpg` | render_thumb |
  | `other` | (none) |

  Note the CAD ordering: `extract_metadata` for step/iges reads the already-converted GLB (OCCT tessellates once). `render_assembly_thumb` is NOT in the map — it is triggered per-revision (Task 6).

Task args are `(job_id: str, blob_hash: str)` (assembly: `(job_id: str, revision_id: int)`), dispatched with `task_id=str(job.id)` like M1. Steps are idempotent: if the step's outputs are already `ok` it marks the job done ("skipped: already present") and still enqueues the next step. Events reuse the existing `job.updated` shape — no new event types.
